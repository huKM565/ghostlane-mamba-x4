# Четыре комнаты Mamba в одном VLESS-туннеле на Android

## Контекст

Нужен пропатченный APK на основе оригинального Ghostlane 1.0.472. Один профиль Mamba должен одновременно использовать четыре комнаты, пропускать через них VLESS с `xudp` и предоставлять приложениям один туннель. Отдельный профиль VK Calls должен продолжить работать без изменений.

Текущий Android-клиент запускает один `mobile.Runtime`. Список `##rooms` служит только для failover. VLESS и olcRTC запускаются как несвязанные виды профилей, поэтому штатная подписка не может объединить комнаты или направить VLESS через них.

## Требования

- База: Ghostlane 1.0.472, Android APK.
- Один составной профиль Mamba запускает ровно четыре комнаты одновременно.
- Каждая комната имеет собственный `mobile.Runtime` и loopback SOCKS5-порт.
- Xray создаёт четыре VLESS-outbound с Mux/XUDP; каждый направлен через свою комнату с помощью `streamSettings.sockopt.dialerProxy`.
- Общий Xray balancer со стратегией `roundRobin` распределяет новые соединения между четырьмя VLESS-outbound.
- sing-box остаётся внешним core для существующей маршрутизации и направляет трафик в SOCKS inbound Xray; официальный sing-box 1.13.14 не поддерживает `loadbalance`.
- Android использует существующий TUN и `hev-socks5-tunnel`; для пользователя это один профиль и одна кнопка.
- Комнаты, olcRTC-ключ и VLESS-параметры приходят из подписки и не зашиваются в APK.
- VK Calls остаётся отдельным независимым профилем в той же подписке.
- Обычные olcRTC-профили, failover через `##rooms` и обычные VLESS-профили сохраняют прежнее поведение.

## Не входит в задачу

- Попакетный бондинг одного TCP-соединения.
- Объединение VK Calls с четырьмя комнатами Mamba.
- Изменение wire-протокола olcRTC.
- Перенос закрытого PR olcRTC #138.
- Патч только `libgojni.so` без изменения Android-оркестрации.
- Изменение серверного протокола или обязательное обновление существующих olcRTC-релеев.

Балансировка выполняется по соединениям. Несколько соединений могут использовать разные комнаты и суммировать пропускную способность; одно TCP-соединение остаётся на одной комнате.

## Формат подписки

Составной профиль записывается одной olcRTC-ссылкой, существующим заголовком `##rooms` и новым заголовком `##bond-vless`:

```text
olcrtc://jitsi?datachannel@https://meet.mamba.group/room-1#OLCRTC_KEY$Mamba x4
##rooms: https://meet.mamba.group/room-2, https://meet.mamba.group/room-3, https://meet.mamba.group/room-4
##bond-vless: vless://VLESS_UUID@127.0.0.1:10000?security=none&encryption=none#VLESS-through-Mamba

olcrtc://vkcalls?vp8channel@https://vk.ru/call/join/ROOM#OLCRTC_KEY$VK Calls
```

`##bond-vless` относится к непосредственно предшествующей olcRTC-ссылке. При его наличии основная комната и три дополнительные образуют пул из четырёх путей, а не список failover.

Правила:

- В пуле должно быть ровно четыре уникальные непустые комнаты: одна основная и три дополнительные.
- Все комнаты используют provider, transport и olcRTC-ключ основной ссылки.
- `##bond-vless` обязан содержать корректную VLESS-ссылку, которую принимает существующий `LinkParser`.
- VLESS-адрес `127.0.0.1:10000` означает Xray на стороне olcRTC-выхода, а не loopback телефона: TCP к этому адресу открывает серверный olcRTC.
- Без `##bond-vless` заголовок `##rooms` сохраняет старое значение failover.
- Официальный клиент может игнорировать неизвестный заголовок; пропатченный клиент обязан распарсить его и сохранить при обновлении подписки.

## Модель данных

`LocationConfig` получает необязательное сохраняемое поле `bondVlessLink` (`bond_vless`).

- `LocationsDatasource` заполняет его из `fields["bond-vless"]` при разборе текстовой olcRTC-подписки.
- `normalized()` очищает значение от внешних пробелов.
- Проверка составного профиля подтверждает четыре комнаты и успешный разбор VLESS-ссылки.
- Существующие `id`, `key`, `bypassProvider`, `transport` описывают несущие комнаты.
- `rawLink`, `kind` и существующие поля обычных VLESS-профилей не меняют смысл.
- `LocationEntry` также хранит `bond_vless` и передаёт его в обоих направлениях через `location`, `from` и `normalized()`, иначе первая запись профиля потеряет маркер.
- Сериализация сохраняет поле в локальном хранилище и при последующих обновлениях подписки.

## Запуск составного профиля

`OlcboxVpnService.startTransport` выбирает отдельную ветку только для `LocationKind.Olcrtc` с непустым `bondVlessLink`.

1. Остановить предыдущие runtime и core-процессы.
2. Получить четыре свободных loopback-порта для комнат, порт Xray и отдельный порт для основного sing-box SOCKS inbound.
3. Создать четыре независимых `mobile.Runtime` через `Mobile.new_()`.
4. Для каждого runtime установить socket protector, DNS текущей upstream-сети, provider, transport, device ID, общий olcRTC-ключ, свою комнату и свой SOCKS-порт.
5. Не передавать комнаты пула как failover внутри каждого runtime.
6. Запустить все четыре runtime и дождаться первой готовой комнаты. Она сразу запускает туннель; остальные готовятся и добавляются через recovery. Ошибка только если ни одна комната не готова.
7. Разобрать `bondVlessLink` в `OutboundSpec.Vless` и запустить Xray с объединённой конфигурацией.
8. Запустить sing-box с существующей SOCKS-chain конфигурацией перед Xray, сохранив выбранный routing mode.
9. Назначить `activeCorePort` и `activeCoreLogin` основного sing-box, чтобы существующий TUN, проверка трафика и bridge использовали его как обычный core.
10. После проверки готовности портов и живости всех процессов разрешить перевод профиля в Connected.

Пул использует одинаковые SOCKS-учётные данные для всех четырёх runtime. Порты не фиксируются как 1081-1084 в коде: они выделяются динамически и явно передаются в конфигуратор Xray.

## Конфигурация Xray и sing-box

В `XrayConfig` отдельный построитель составного профиля принимает от одного до четырёх активных портов. Для каждого создаются:

- `socks-room-N`: SOCKS5 `127.0.0.1:<roomPort>`, с учётными данными runtime.
- `vless-room-N`: одинаковый plain TCP VLESS с `dialerProxy=socks-room-N` и Mux/XUDP (`concurrency=-1`, `xudpConcurrency=16`, UDP/443 разрешён).
- `bond`: balancer только с активными VLESS-тегами и стратегией `roundRobin`.

Весь трафик SOCKS inbound Xray направляется правилом в `bond`. Для текущего сервера используется plain VLESS без дополнительного TLS внутри уже защищённого WebRTC-канала.

Существующий `SingBoxConfig.buildSocksChain` ставится перед Xray. Его основной `out` по-прежнему обслуживает правила маршрутизации и DNS, поэтому официальный sing-box не требует патча или неподдерживаемого `loadbalance`.

## Остановка и ошибки

Для пула хранится отдельный список четырёх runtime; существующий одиночный runtime не используется одновременно с ним.

- Одна неподнявшаяся комната останавливается и исключается; запуск продолжается на оставшихся.
- Если не готова ни одна комната, запуск считается неуспешным и останавливает весь пул.
- Xray roundRobin получает только активные порты, поэтому мёртвая комната не получает новые соединения.
- Watchdog переподключает выпавшую комнату; при изменении активного набора Xray и sing-box пересобираются на том же входном порту TUN.
- Составной профиль работает при одной или нескольких (до четырёх) живых runtime и живых Xray/sing-box.
- При остановке, смене профиля, потере сети и отмене корутины очищаются все четыре runtime, включая неактивные.
- Обновление DNS применяется ко всем runtime пула.
- Переход между составной Mamba, VK Calls, одиночной Mamba и обычным VLESS не оставляет процессов или занятых портов от предыдущего профиля.
- Выбранная карточка показывает номера комнат 1–4: зелёный — runtime активен, красный — не активен.

## Совместимость VK Calls и остальных профилей

VK Calls не получает `##bond-vless`, поэтому использует существующую ветку `startMobile` с одним runtime. Проверяются оба направления переключения:

- составная Mamba -> VK Calls;
- VK Calls -> составная Mamba.

Обычная Jitsi/Mamba-ссылка без маркера продолжает использовать `##rooms` только как failover. Обычная VLESS-ссылка без olcRTC-комнат продолжает подключаться напрямую.

## Тестирование

### Модель и подписка

В существующих common-тестах `LocationsRepositoryImplTest` и связанных тестах сериализации:

- разбор составного профиля сохраняет VLESS-ссылку и четыре комнаты;
- порядок комнат: основная, затем три дополнительные;
- дубликаты и недостающие комнаты отклоняются;
- неверная или не-VLESS ссылка в `##bond-vless` отклоняется;
- VK Calls и обычная Mamba без маркера не становятся составными;
- обычный `##rooms` остаётся failover;
- поле переживает сериализацию и повторный разбор.

### Конфигурация Xray

В `XrayConfigBondTest` и `XrayConfigDumpTest`:

- создаются четыре SOCKS и четыре VLESS-outbound;
- каждый VLESS имеет Mux/XUDP и правильный `dialerProxy`;
- `bond` является balancer со стратегией `roundRobin` и всеми четырьмя путями;
- SOCKS-учётные данные и основной inbound совпадают;
- выбранный routing mode сохраняется существующим sing-box front;
- сгенерированный JSON проходит `xray run -test` закреплённой версии 26.7.11.

### Жизненный цикл Android

Общая логика планирования пула выделяется из Android Service настолько, чтобы проверить без устройства:

- назначаются четыре разные комнаты и четыре разных порта;
- ни одна комната не используется как failover другой;
- первая готовая комната запускает туннель, а остальные доучиваются через recovery;
- отсутствие готовых комнат вызывает остановку всех созданных компонентов;
- остановка и смена профиля очищают весь пул;
- одиночный runtime и пул не считаются живыми одновременно.

Доступные Android/JVM-тесты и сборка APK являются обязательными. Если для `mobile.Runtime` невозможен JVM-тест, проверяется чистая оркестрационная модель, а реальный запуск проверяется отдельно на устройстве.

### Сквозная проверка

На существующих четырёх Mamba-релеях и Xray:

1. Импортировать тестовую подписку с составной Mamba и отдельным VK Calls.
2. Убедиться, что в списке один составной профиль Mamba и один VK Calls.
3. Подключить Mamba и проверить четыре одновременных olcRTC-сеанса и четыре SOCKS-порта.
4. Проверить выходной IP и прохождение TCP через VLESS.
5. Проверить UDP через `xudp`, включая DNS-запрос и фактический Discord Voice на Android.
6. Несколькими параллельными соединениями убедиться, что используются разные пути; не выдавать этот тест за попакетный бондинг.
7. Переключиться на VK Calls и проверить трафик через него без запущенного пула Mamba.
8. Переключиться обратно и убедиться в повторном запуске всех четырёх комнат.
9. Проверить остановку и повторное подключение без занятых портов.

## Сборка и поставка

- Собирается полный APK из исходников Ghostlane 1.0.472, а не подмена одной библиотеки в ранее пропатченном APK.
- Нативные olcRTC, sing-box и Xray берутся в версиях, закреплённых оригинальным релизом.
- Проверяются ABI, выравнивание APK и подпись.
- Готовый APK сохраняется отдельно от `Ghostlane-patched.apk`, чтобы не смешивать новый результат с неполной сборкой Antigravity.
- В поставку включаются пример подписки без реальных секретов и итог выполненных проверок.

## Принятые решения

- Реализация находится в приложении и использует существующие olcRTC и sing-box без изменения их протоколов.
- Для успешного старта достаточно одной комнаты; остальные переподключаются в фоне.
- VK Calls остаётся отдельным профилем.
- Составной режим включается только явным `##bond-vless`.
- Не заявляется агрегация одного TCP-потока или незаметный failover отдельной комнаты.
