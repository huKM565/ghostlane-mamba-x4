# ИлюхаLine: SaluteJazz 4x

## Контекст и результат

Пользователь выбрал SaluteJazz как дополнительный транспорт для ИлюхаLine. MTS Link не входит: постоянные MTS-комнаты пришлось бы создавать вручную. WB Stream, MAX, Телемост и новые Multi-профили не добавляются.

На каждой из двух существующих VDS появляется профиль `SaluteJazz 4x`: четыре независимые SaluteJazz-комнаты через `datachannel`. Вместе с существующими Mamba 4x и VK 4x подписка будет содержать шесть профилей:

- Германия — Mamba 4x (пойдет для мобильного интернета);
- Германия — VK 4x (обход белых списков);
- Германия — SaluteJazz 4x;
- Финляндия — Mamba 4x (пойдет для мобильного интернета);
- Финляндия — VK 4x (обход белых списков);
- Финляндия — SaluteJazz 4x.

Существующие названия Mamba/VK, комнаты, ключи, VLESS и подписка сохраняются. Multi остаётся удалённым из новых подписок.

## Согласованный порядок внедрения

Сначала выполняется одиночный live-тест SaluteJazz на локальном Linux-клиенте и сервере. Он проверяет возможность анонимного создания комнаты, входа обеих сторон, handshake и прохождения TCP и UDP. Это временный тест, его процессы и конфиги удаляются после завершения.

Если одиночный тест успешен, на Германии и Финляндии разворачиваются четыре постоянные SaluteJazz-комнаты на каждую VDS. Если создание или живой тест не работает, полный 4x не разворачивается; результат сообщается пользователю без маскировки проблемы.

## Комнаты и ключи

SaluteJazz не требует аккаунта. Движок уже предоставляет `auth/salutejazz.Provider.CreateRoom`, который одним анонимным запросом создаёт комнату и возвращает ссылку формата `<code>:<password>`.

В olcRTC добавляется небольшая локальная команда для создания комнаты через существующий `CreateRoom`. Она не дублирует HTTP API в deploy-скрипте и не меняет wire-протокол или mobile runtime. Unit-тесты команды подставляют fake room creator; существующие provider-тесты используют fake HTTP server. Live-создание не запускается в обычном CI.

Для каждой VDS создаются четыре разные комнаты и один общий 64-hex olcRTC key внутри однородной группы 4x. Ссылки и ключи записываются только в отдельный защищённый локальный файл режима `600` рядом с существующими конфигами `/home/hukm/.config/ilyukhaline/`.

Повторный provision не создаёт дубликаты: валидные сохранённые ссылки переиспользуются, отсутствующие заполняются атомарно. Парольная часть ссылки, ключи и URL подписки не выводятся в логи и не коммитятся. У SaluteJazz нет операции удаления комнаты, поэтому provision не запускается повторно без необходимости.

## Серверная архитектура

На каждой VDS добавляются четыре systemd-экземпляра с метками `j1–j4`:

```text
provider: salutejazz
transport: datachannel
room.id: <code>:<password>
egress.allow: существующий точный loopback VLESS IP:port
```

Всего на VDS становится двенадцать olcRTC-сервисов: четыре Mamba, четыре VK и четыре SaluteJazz. Все ведут в существующий Xray/VLESS inbound. Отдельный Xray, отдельные public listeners и связка ВДС между собой не создаются.

В защищённых реальных конфигах добавляется `SALUTEJAZZ_ENABLED=true` и путь к защищённому файлу комнат. Значение по умолчанию в скрипте — `false`, чтобы старые конфиги и воспроизводимые тесты не начинали создавать внешние комнаты.

Перед deploy проверяются доступные RAM, CPU и диск. Mamba, VK, Xray и неуправляемые 3x-ui, Hysteria, Amnezia и WD TT не перезапускаются при добавлении SaluteJazz, если их собственные конфиги не изменились. SaluteJazz использует обычный `RestartSec=30s`, не VK-specific 300 секунд.

Все серверные изменения выполняются через `scripts/deploy-olcrtc-vds.sh`. Повторный deploy принимает существующие `j1–j4` YAML и сохраняет их комнаты и ключи. Rollback затрагивает только управляемые SaluteJazz-изменения и восстанавливает прежнее состояние остальных сервисов.

## Подписка

`deploy/generate_subscription.py` принимает необязательную группу `j1–j4` в managed bundle. Допустимы только ноль или четыре SaluteJazz-комнаты; неполная группа отклоняется.

Генератор добавляет `SaluteJazz 4x` между VK и следующей VDS-группой. При одинаковом ключе используется существующий компактный формат:

```text
olcrtc://salutejazz?datachannel@ROOM_REF_1#KEY$Германия — SaluteJazz 4x
##group: Германия
##rooms: ROOM_REF_2, ROOM_REF_3, ROOM_REF_4
##bond-vless: vless://UUID@127.0.0.1:10000?security=none&encryption=none#VLESS
```

При разных фактических ключах используются полные `##bond-room`, как для принятых старых Mamba/VK. Генератор по-прежнему не создаёт Multi или Телемост для финальных реальных конфигов.

Публикация выполняется на тот же секретный HTTPS URL `sub.hukm.dev` через существующий publisher. Подписка импортируется как шесть профилей в двух группах. Неудачный refresh сохраняет предыдущий рабочий список.

## Приложение

`LocationConfig` уже поддерживает `salutejazz` и единственный допустимый транспорт `datachannel`; Android и Desktop уже передают provider, room и key в olcRTC. Изменения ограничиваются тестами импорта/планирования и отображением меток комнат.

Для SaluteJazz используются метки `J1–J4`. Зелёный цвет означает активный путь, красный — неактивный. Поскольку provider не отдаёт приложению достоверный occupancy через текущий патч, активная комната показывает `✓`, а не выдуманное число участников. Ошибки входа и relay используют существующие сообщения.

Старые импортированные профили, включая совместимость 8/12 путей, не удаляются кодом приложения.

## Обработка ошибок

- Ошибка создания комнаты прерывает provision до изменения ВДС.
- Невалидная или неполная группа ссылок отклоняется локально.
- Ошибка одного сервиса `j*` вызывает rollback deploy по существующим правилам.
- Во время работы одна выпавшая комната исключается из balancer; остальные продолжают туннель.
- Неудачный rebalance восстанавливает прежний рабочий набор портов.
- Если все четыре пути потеряны, выполняется существующий полный recovery.
- Логи не содержат `<code>:<password>`, olcRTC keys, UUID или секретный URL подписки.

## Проверки

1. Go unit/race/lint/build для команды создания комнаты; обычный CI не обращается к живому SaluteJazz.
2. Временный одиночный live-тест: создание комнаты, клиент и сервер, SOCKS, TCP и UDP.
3. JVM-тесты: SaluteJazz 4x import, полные пути, `J1–J4`, неизменность Mamba/VK и отказ неполной группы.
4. Offline deploy-тесты: provision idempotence, четыре комнаты, режим `600`, adoption, rollback, отсутствие секретов и сохранение неуправляемых сервисов.
5. `bash -n`, ShellCheck, все deploy/gate-тесты и pinned sing-box/Xray config checks.
6. Реальный deploy по четыре комнаты на Германию и Финляндию без перезапуска Mamba/VK.
7. Импорт HTTPS-подписки: ровно шесть профилей, без Multi/Телемоста/MTS.
8. Android smoke для SaluteJazz 4x каждой группы: состояние Connected и реальные TCP/UDP-записи Xray на соответствующей VDS, без обязательных ipify-запросов.
9. Потеря одной комнаты не роняет туннель; индикаторы отражают активные пути.
10. Windows CI и свежие артефакты, поскольку Desktop использует те же четыре пути.

## Не входит

- MTS Link, WB Stream, MAX и Телемост.
- Новые Multi-профили и связка Германия↔Финляндия.
- Попакетный бондинг одного соединения или обещание суммарной скорости.
- Изменение протокола SaluteJazz/olcRTC.
- Создание комнат вручную пользователем.
- Изменение других VPN и сайтов на серверах.
