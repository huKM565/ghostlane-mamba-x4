# ИлюхаLine: VK 4x, Телемост 4x и смешанные Multi

## Контекст и результат

В ИлюхаLine уже работает Mamba 4x на Android и Windows: четыре независимые Mamba-комнаты через DataChannel объединяются клиентским Xray в один VLESS-туннель. Нужно распространить тот же принцип на VK Calls и Яндекс.Телемост, добавить смешанные профили и настроить две VDS через один воспроизводимый Linux-скрипт.

Для каждой VDS в одной подписке должно быть пять профилей:

- Mamba 4x: четыре Mamba/Jitsi-комнаты через DataChannel;
- VK 4x: четыре VK Calls через VP8;
- Телемост 4x: четыре постоянные встречи Яндекс.Телемоста через VP8;
- Multi VK + Mamba: четыре VK и четыре Mamba, всего восемь комнат;
- Multi Телемост + Mamba: четыре Телемоста и четыре Mamba, всего восемь комнат.

Группы в подписке называются `Германия` и `Финляндия`. Германия — существующая VDS `87.120.84.241`; Финляндия — `magic.covertspot.ru` (`185.216.71.37`). Суммарно в подписке десять профилей.

Для пользователя каждый профиль остаётся одним сервером с одной кнопкой подключения. Смешивание DataChannel и VP8 разрешено: Xray работает с локальными SOCKS-портами и не зависит от способа, которым olcRTC переносит байты через видеозвонок.

## Общий подход

Существующий Mamba-пул обобщается до пула независимых olcRTC-путей. Не создаются пять разных реализаций и не добавляется серверный бондинг.

Каждый путь описывается собственными значениями:

- room URL;
- olcRTC key;
- provider;
- transport.

На Android каждый путь получает собственный `mobile.Runtime`; на Windows — собственный процесс pinned olcRTC. Каждый путь слушает отдельный loopback SOCKS5-порт с общими учётными данными текущего запуска.

Клиентский Xray создаёт по VLESS-outbound на активный путь и направляет каждый через соответствующий SOCKS с помощью `dialerProxy`. Общий balancer со стратегией `roundRobin` принимает от одного до восьми активных путей. Существующий sing-box front, TUN, правила маршрутизации, Mux и XUDP сохраняются.

Одно соединение остаётся на одном пути. Разные соединения могут использовать разные пути и суммировать их пропускную способность; попакетный бондинг одного TCP-соединения не заявляется.

## Жизненный цикл и ошибки

Поведение всех профилей 4x и Multi одинаковое:

- запускаются все четыре или восемь путей;
- первая готовая комната сразу разрешает запуск туннеля;
- остальные комнаты подключаются и добавляются в balancer без смены TUN-facing порта;
- неподнявшаяся или выпавшая комната исключается из balancer и переподключается независимо;
- работа продолжается, пока жив хотя бы один путь и оба core;
- полный recovery выполняется только при потере всех путей;
- остановка, смена профиля, потеря сети и отмена запуска очищают весь пул;
- обновление DNS применяется ко всем путям;
- переходы между обычными olcRTC, 4x, Multi и обычными core-профилями не оставляют старых процессов или занятых портов.

Фиксированные проверки `size == 4`, списки из четырёх индикаторов и имена логов `Mamba x4` заменяются моделью, поддерживающей четыре и восемь путей. Существующие одиночные olcRTC и failover через `##rooms` без `##bond-vless` сохраняют прежнее поведение.

## Модель и формат подписки

В `LocationConfig` добавляется сохраняемое поле `bondedRoomConfigs: List<BondRoomConfig>` с сериализацией как `bonded_rooms`. `BondRoomConfig` содержит room, key, provider и transport. Старые `failoverRoomIds` и `bondVlessLink` сохраняются для совместимости.

Для однородных профилей 4x продолжает работать текущий формат: основная olcRTC-ссылка, три дополнительные комнаты в `##rooms` и `##bond-vless`. Он подходит для Mamba, VK и Телемоста.

Для Multi добавляются повторяемые строки `##bond-room`, каждая содержит одну полную olcRTC-ссылку. Основная ссылка профиля является первым путём, далее следуют семь `##bond-room`. Полные ссылки позволяют задать разные provider, transport и ключи без неоднозначного разбора списка через запятую.

Схематичный пример без секретов:

```text
olcrtc://jitsi?datachannel@MAMBA_ROOM_1#KEY$Германия — Multi VK + Mamba
##bond-room: olcrtc://jitsi?datachannel@MAMBA_ROOM_2#KEY
##bond-room: olcrtc://jitsi?datachannel@MAMBA_ROOM_3#KEY
##bond-room: olcrtc://jitsi?datachannel@MAMBA_ROOM_4#KEY
##bond-room: olcrtc://vkcalls?vp8channel@VK_ROOM_1#KEY
##bond-room: olcrtc://vkcalls?vp8channel@VK_ROOM_2#KEY
##bond-room: olcrtc://vkcalls?vp8channel@VK_ROOM_3#KEY
##bond-room: olcrtc://vkcalls?vp8channel@VK_ROOM_4#KEY
##bond-vless: vless://VLESS_UUID@127.0.0.1:10000?security=none&encryption=none#VLESS
```

Парсер заголовков должен сохранять повторяемые `##bond-room` как список; остальные заголовки сохраняют текущие правила. Порядок путей совпадает с порядком в подписке.

Проверки модели:

- составной профиль содержит ровно четыре или восемь путей;
- Multi из подписки содержит ровно четыре Mamba и четыре комнаты второго provider;
- каждый путь имеет непустые room и key;
- provider и transport совместимы;
- комбинации provider + room не повторяются;
- `##bond-vless` содержит корректный VLESS;
- явные пути Multi переживают сериализацию, импорт и обновление подписки;
- старые Mamba 4x преобразуются в общий список путей без изменения их подписки.

Все реальные комнаты, olcRTC-ключи и VLESS UUID находятся только в подписке и серверных конфигах. Они не вшиваются в APK, Windows-пакет или Git.

## Подписка и публикация

Создаётся одна текстовая подписка с десятью профилями. Сначала идут пять профилей группы `Германия`, затем пять профилей группы `Финляндия`.

Скрипт развёртывания генерирует подписку из фактических управляемых конфигов VDS, а не из второй ручной копии параметров. Это исключает расхождение комнат и ключей между сервером и клиентом. Локальный генератор подписки имеет отдельную команду и может вывести файл без публикации.

Для импорта по URL файл публикуется по HTTPS на существующем nginx одной из VDS по отдельному трудно угадываемому пути. Directory listing не включается, существующие сайты, 3x-ui, Hysteria и VPN-инбаунды не изменяются. URL и содержимое подписки не коммитятся.

## Серверная схема

На каждой VDS работают двенадцать независимых olcRTC-сервисов:

- четыре Mamba;
- четыре VK Calls;
- четыре Телемоста.

Оба Multi используют комнаты из этого общего набора. Отдельные процессы для Multi не создаются: каждый профиль Multi выбирает нужные восемь из уже работающих двенадцати.

Каждый olcRTC-сервис направляет принятые подключения в один выделенный VLESS-вход Xray на loopback VDS, по умолчанию `127.0.0.1:10000`. Xray выпускает трафик в интернет. VLESS-вход не публикуется наружу и не меняет существующие инбаунды 3x-ui.

Для Германии сохраняются текущие комнаты и ключи, чтобы не сломать существующие клиенты и роутер. Существующие одиночные Mamba и VK становятся первыми комнатами соответствующих 4x и переводятся под управление скрипта; два сервиса не должны одновременно выполнять одну серверную роль в одной комнате. Текущий dedicated Xray переиспользуется после проверки конфигурации.

Для Телемоста используются постоянные запланированные встречи. Временные ссылки со сроком жизни 24 часа не подходят.

Перед установкой проверяются RAM, CPU, диск, занятые порты, текущие systemd-сервисы и существующие VPN. На слабой VDS olcRTC не компилируется: pinned бинарник собирается и тестируется на Linux-компьютере, затем загружается на VDS.

## Linux-скрипт развёртывания

Добавляется `scripts/deploy-olcrtc-vds.sh` и пример конфигурации без секретов. Скрипт запускается на Linux-компьютере и выполняет операции на VDS через SSH. Оба сервера настраиваются только через него.

Основные команды:

- `check`: подключение по SSH, ОС, ресурсы, порты, существующие сервисы и доступность всех room URL;
- `build`: локальная сборка закреплённого olcRTC с применёнными патчами и проверка бинарника;
- `deploy`: загрузка бинарника, управляемые конфиги, systemd units, выделенный Xray, запуск и проверка;
- `subscription`: генерация локального файла подписки из управляемых конфигов;
- `publish`: публикация уже сгенерированной подписки по HTTPS;
- `status`: состояние двенадцати комнат, Xray и занятых loopback-портов.

Параметры VDS, комнаты и секреты задаются в отдельном локальном конфиге с правами владельца. Пример в Git содержит только placeholders. Повторный deploy идемпотентен: не генерирует заново существующие ключи, не меняет комнаты и не перезаписывает неуправляемые сервисы.

Скрипт управляет только собственными файлами и units с префиксом `ilyukhaline-`. Он не удаляет и не переустанавливает 3x-ui, Hysteria, Amnezia, nginx или другие VPN. Новые файлы загружаются во временные пути и проходят проверки до замены текущих. Перед заменой бинарника и конфигов создаются резервные копии. При ошибке обязательного этапа скрипт останавливает вновь запущенные units и восстанавливает предыдущие файлы и сервисы из резервных копий.

Порядок внедрения:

1. Написать скрипт и проверить его синтаксис, тесты и `check` без изменений на обеих VDS.
2. Запустить deploy на Германии, сохранив существующие комнаты и проверив прежние клиенты.
3. Проверить все пять немецких профилей end-to-end.
4. Тем же скриптом настроить Финляндию.
5. Проверить все пять финских профилей, затем сгенерировать и опубликовать общую подписку.

## Интерфейс

Список показывает десять профилей в группах `Германия` и `Финляндия`. Для выбранного составного профиля отображаются подписи `M1–M4`, `V1–V4` и `T1–T4` в зависимости от его состава.

Состояния:

- зелёный — путь активен и участвует в balancer;
- красный — путь не активен;
- `Подключение не удалось` — клиент не смог войти в комнату или потерял собственное соединение;
- `Сервер не смог подключиться` — клиент вошёл в комнату, но relay не присутствует или не завершил handshake.

Для различения ошибок в olcRTC добавляются явные события `roomJoined` и `relayReady`; не допускается угадывать причину только по таймауту. События работают для Jitsi, VK Calls и Телемоста и сохраняются в состоянии комнаты при повторном открытии приложения.

Число людей не включает VDS. Для активной Mamba-комнаты отображается `max(rawParticipants - 1, 0)`: локальный клиент и другие пользователи остаются, relay вычитается. Если relay отсутствует, вычитание не выполняется. Для VK и Телемоста число показывается только при наличии настоящего occupancy от provider; иначе отображается `—`, а не выдуманное значение.

Из интерфейса убираются фильтры транспортов, ping и его кнопки, места и их графики, ссылки на сайт и поддержку Ghostlane. Остаются профили, подключение, состояния комнат, добавление и обновление подписки и основные настройки. Ранее отключённые обновления до Ghostlane не возвращаются.

## Тестирование

### Модель, подписка и Xray

- Импорт и сериализация всех пяти видов профилей.
- Старый Mamba 4x и обычный failover остаются совместимыми.
- Multi сохраняет восемь полных путей с разными provider и transport.
- Отклоняются неверные ключи, дубликаты, неподдерживаемые транспорты и неправильное число комнат.
- Xray принимает от одного до восьми портов и создаёт корректный roundRobin только на активных путях.
- Сгенерированные конфиги проходят pinned `xray run -test` и существующие sing-box checks.

### Android и Windows

- Запуск 4x и Multi, начиная с первой готовой комнаты.
- Добавление остальных комнат без пересоздания TUN-facing порта.
- Потеря любой одной комнаты не роняет профиль.
- Потеря всех комнат вызывает полный recovery.
- Переключения между всеми пятью профилями очищают предыдущий пул.
- Статусы, причины ошибок и occupancy соответствуют событиям движка.
- Существующие JVM/common-тесты, Android APK и Windows packaging проходят.

### Скрипт и VDS

- `bash -n`, ShellCheck и тесты идемпотентности на локальных фикстурах.
- `check` ничего не меняет на VDS.
- Повторный deploy не меняет ключи, комнаты и неуправляемые файлы.
- На обеих VDS запущены четыре Mamba, четыре VK и четыре Телемоста плюс один выделенный Xray.
- Старые клиенты Германии продолжают работать.
- Для каждого из десяти профилей проверяются выходной IP, TCP и UDP через XUDP.
- Несколькими параллельными соединениями подтверждается использование разных путей без заявления о попакетном бондинге.
- Подписка импортируется на Android и Windows и обновляется без потери Multi.

## Не входит

- Попакетный бондинг одного соединения.
- Бондинг или изменение wire-протокола olcRTC на VDS.
- Перенос новых пулов на Linux/macOS/iOS-клиенты.
- Автоматическое обновление приложения.
- Удаление или изменение других VPN-сервисов на VDS.
