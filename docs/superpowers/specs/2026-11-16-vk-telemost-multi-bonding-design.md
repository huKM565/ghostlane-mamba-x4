# ИлюхаLine: Mamba 4x, VK 4x и Multi 8x

## Контекст и результат

ИлюхаLine объединяет независимые olcRTC-комнаты в один VLESS-туннель на Android и Windows. По решению пользователя Яндекс.Телемост полностью исключён из развёртывания и подписки. Для каждой VDS создаются три профиля:

- Mamba 4x: четыре Mamba/Jitsi-комнаты через DataChannel;
- VK 4x: четыре VK Calls через VP8;
- Multi 8x: четыре Mamba и четыре VK, всего восемь комнат.

Группы называются `Германия` и `Финляндия`. Германия — `87.120.84.241`; Финляндия — `magic.covertspot.ru` (`185.216.71.37`). Общая подписка содержит шесть профилей, по три на группу.

Для пользователя каждый профиль остаётся одним сервером с одной кнопкой подключения. DataChannel и VP8 можно смешивать: Xray работает с локальными SOCKS-портами и не зависит от способа переноса байтов через видеозвонок.

## Архитектура и жизненный цикл

Каждый путь имеет собственные room URL, olcRTC key, provider и transport. На Android ему выделяется `mobile.Runtime`, на Windows — отдельный процесс pinned olcRTC. Каждый путь слушает отдельный loopback SOCKS5-порт.

Клиентский Xray создаёт VLESS-outbound на активный путь и направляет его через соответствующий SOCKS с помощью `dialerProxy`. Balancer `roundRobin` принимает от одного до двенадцати активных путей. Sing-box front, TUN, маршрутизация, Mux и XUDP сохраняются.

Одно соединение остаётся на одном пути. Разные соединения могут использовать разные пути; попакетный бондинг одного TCP-соединения не заявляется.

Для профилей 4x и Multi:

- первая готовая комната сразу разрешает запуск туннеля;
- остальные комнаты подключаются и добавляются в balancer без смены TUN-facing порта;
- выпавшая комната исключается из balancer и переподключается независимо;
- работа продолжается, пока жив хотя бы один путь и оба core;
- полный recovery выполняется только при потере всех путей;
- остановка, смена профиля, потеря сети и отмена запуска очищают пул;
- обновление DNS применяется ко всем путям.

Модель принимает 4, 8 и 12 путей. Поддержка 12 сохраняется для старых импортированных подписок, но новая серверная схема использует только 4 и 8.

## Модель и формат подписки

`LocationConfig.bondedRoomConfigs` сериализуется как `bonded_rooms`. `BondRoomConfig` содержит room, key, provider и transport. Старые `failoverRoomIds` и `bondVlessLink` сохраняются.

Однородный 4x использует основную olcRTC-ссылку, три дополнительные комнаты в `##rooms` и `##bond-vless`. Если фактические ключи принятых старых комнат различаются, генератор вместо `##rooms` выписывает полные `##bond-room` ссылки, сохраняя каждый ключ.

Multi использует основную ссылку и семь повторяемых `##bond-room` для Multi 8x. Полные ссылки задают provider, transport и ключ каждого пути. Порядок путей совпадает с порядком в подписке.

Пример без секретов:

```text
olcrtc://jitsi?datachannel@MAMBA_ROOM_1#KEY$Германия — Multi 8x
##bond-room: olcrtc://jitsi?datachannel@MAMBA_ROOM_2#KEY
##bond-room: olcrtc://jitsi?datachannel@MAMBA_ROOM_3#KEY
##bond-room: olcrtc://jitsi?datachannel@MAMBA_ROOM_4#KEY
##bond-room: olcrtc://vkcalls?vp8channel@VK_ROOM_1#KEY
##bond-room: olcrtc://vkcalls?vp8channel@VK_ROOM_2#KEY
##bond-room: olcrtc://vkcalls?vp8channel@VK_ROOM_3#KEY
##bond-room: olcrtc://vkcalls?vp8channel@VK_ROOM_4#KEY
##bond-vless: vless://VLESS_UUID@127.0.0.1:10000?security=none&encryption=none#VLESS
```

Проверяются непустые room и key, совместимость provider и transport, уникальность provider + room, число путей и корректность VLESS. Явные пути переживают сериализацию, импорт и обновление подписки. Реальные комнаты, ключи и UUID не коммитятся и не вшиваются в приложение.

## Подписка и публикация

Генератор читает фактические управляемые конфиги обеих VDS и выводит шесть профилей: сначала три немецких, затем три финских. Локальный файл имеет режим `600`.

Файл публикуется на `192.168.31.82` через выделенный HTTPS-vhost `sub.hukm.dev` по отдельному трудно угадываемому пути. `l.hukm.dev` остаётся только для сокращения ссылок. Directory listing выключен. Nginx читает файл через режим `640 root:www-data`; остальные сайты и VPN не изменяются. URL и содержимое подписки не коммитятся.

## Серверная схема

На каждой VDS работают восемь независимых olcRTC-сервисов: четыре Mamba и четыре VK Calls. Multi 8x использует тот же набор; отдельные процессы для Multi не создаются.

Каждый olcRTC-сервис направляет принятые подключения в выделенный VLESS-вход Xray на loopback VDS, по умолчанию `127.0.0.1:10000`. В YAML задаётся `egress.allow` с этим точным `IP:port`: иначе политика olcRTC отклоняет loopback как `blocked target`. Исключение действует только на этот адрес и порт для TCP и UDP; остальные частные адресаты запрещены.

На Германии для существующих клиентов сохраняется listener `0.0.0.0:10000` через `VLESS_PUBLIC_COMPAT=true`. Генерируемая подписка всё равно использует `127.0.0.1` как цель на стороне VDS. Старые комнаты и ключи сохраняются; при переносе YAML добавляется или обновляется только `egress.allow`.

`TELEMOST_ENABLED=false` исключает Телемост из генерации. Deploy отключает и удаляет его управляемые units и YAML, не меняя Mamba/VK. Во время фактического удаления уже активные Mamba/VK/Xray не перезапускаются, чтобы не провоцировать VK Flood control. При ошибке удалённые конфиги и ранее активные units восстанавливаются из rollback.

Для VK действует `RestartSec=300s`, для остальных olcRTC — `30s`. Это предотвращает непрерывные запросы к VK API при ошибке входа.

Перед установкой проверяются RAM, CPU, диск, порты, systemd и существующие VPN. olcRTC собирается локально под Linux amd64 и загружается на VDS; компиляция на VDS не выполняется.

## Linux-скрипт развёртывания

Оба сервера настраиваются только через `scripts/deploy-olcrtc-vds.sh`:

- `check`: SSH, ОС, ресурсы, порты и существующие сервисы без изменений;
- `build`: локальная сборка pinned olcRTC и подготовка Xray;
- `deploy`: бинарники, конфиги, units, Xray, запуск, удаление Телемоста и rollback;
- `subscription`: генерация из фактических управляемых конфигов;
- `publish`: атомарная публикация и проверка nginx;
- `status`: состояние восьми комнат и Xray без секретов.

Секреты находятся в отдельных локальных конфигах с правами владельца. Повторный deploy не меняет комнаты, ключи и неуправляемые файлы. 3x-ui, Hysteria, Amnezia, WD TT и другие VPN не удаляются и не переустанавливаются.

## Интерфейс

Список показывает шесть профилей в группах `Германия` и `Финляндия`. Для выбранного профиля отображаются `M1–M4` и `V1–V4` в зависимости от состава.

- Зелёный — путь активен и участвует в balancer.
- Красный — путь не активен.
- `Подключение не удалось` — клиент не смог войти или потерял соединение.
- `Сервер не смог подключиться` — клиент вошёл, но relay отсутствует или не завершил handshake.

Состояния строятся на событиях `roomJoined` и `relayReady`. Occupancy Mamba вычитает relay, если он присутствует. Для VK показывается только настоящий occupancy provider, иначе `—`.

Фильтры транспортов, ping, места и их графики, ссылки на Ghostlane и его обновления удалены. Уведомление VPN называется `ИлюхаLine`; значок приложения — кириллическая буква `И`.

## Проверки

- JVM/common-тесты для 4x, Multi 8x и совместимости со старыми 12x.
- Импорт, сериализация и обновление подписки без потери полных путей.
- Xray принимает 1–12 портов; сгенерированные конфиги проходят pinned Xray и sing-box checks.
- Android и Windows запускаются с первой готовой комнаты, добавляют остальные и переживают потерю отдельных путей.
- `bash -n`, ShellCheck и deploy-тесты проверяют идемпотентность, удаление Телемоста и rollback.
- На обеих VDS работают четыре Mamba, четыре VK и один Xray; Телемост отсутствует.
- На Android проверены IP, TCP и UDP/XUDP для Mamba, VK и Multi 8x обеих групп.
- Подписка импортируется по HTTPS и обновляется без старых Telemost/Multi 12x профилей.

## Не входит

- Яндекс.Телемост в новых профилях и на VDS.
- Попакетный бондинг одного соединения.
- Серверный бондинг или изменение wire-протокола olcRTC.
- Автоматическое обновление приложения.
- Изменение других VPN-сервисов на VDS.
